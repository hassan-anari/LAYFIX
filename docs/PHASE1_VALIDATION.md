# Phase 1 Windows validation

## Evidence boundary

Implementation environment: Linux x64, .NET SDK 10.0.403. Deterministic tests run locally with the native-smoke category excluded. Windows CI additionally executes real Win32 registration/layout enumeration/teardown and a published-process startup/shutdown smoke test. These tests do not generate input or switch an editor's layout. A GitHub-hosted runner is not interactive desktop compatibility evidence.

All human-run rows below are **NOT RUN**. No Windows CPU, memory, latency, DPI, focus-preservation, or editor-compatibility figures are claimed. Use the exact PR head/artifact and record OS/build, keyboard layout IDs, display arrangement/scaling, pass/fail, and sanitized outcome. Do not record typed private text or window contents.

## Preparation

1. On a disposable Windows test account, configure English (US), Persian and Persian Standard in Windows Settings. LAYFIX must never install or remove layouts itself.
2. Download `LAYFIX-win-x64-portable` from the exact successful PR CI run. Extract the artifact wrapper, then extract the inner portable ZIP. Run `Layfix.App.exe` as a normal user with the whole directory present.
3. Check the preview notice and About build identifier. Use a disposable document. Record only layout IDs, status/outcome and pass/fail. The app does not capture text, caret contents or window titles.
4. Use Windows' own language indicator and known disposable sample characters to verify actual editor input. Compare it with the widget, not with LAYFIX's process layout. Open Keyboard settings to inspect loaded layouts and outcomes; Settings itself becomes foreground and should not masquerade as the prior editor.

## Automation and measurements

Run `dotnet restore Layfix.slnx --locked-mode`, `dotnet build Layfix.slnx -c Release --no-restore`, and `dotnet test Layfix.slnx -c Release --no-build --no-restore --logger "trx;LogFileName=test-results.trx"` on Windows. CI rejects zero discovered tests, skipped tests and failures in either project. `NativeSmokeTests` requires Windows APIs, not an interactive editor; classify it separately from these manual rows.

On non-Windows, use `dotnet test Layfix.slnx -c Release --filter "Category!=NativeSmoke"` to run core and fake-boundary adapter tests. The excluded native smoke is **NOT RUN** locally, not counted as a passing native integration.

For idle/performance validation, record hardware, OS, artifact SHA, displays, layout count and Task Manager/Process Explorer samples over 10 minutes idle, 100 explicit switches, then a one-hour mixed session. Record CPU, working/private memory, handle/thread counts and outcome latency without input contents. PASS: bounded steady-state resources, no sustained busy loop, no growing handles after repeated settings/drag/pause sessions, one native request per completed click and no requests at idle. Numerical performance results: **NOT RUN**.

## Known native limits

HKL readback verifies the captured focused thread's conventional keyboard layout. Some third-party TSF services can expose different effective profiles or ignore WM_INPUTLANGCHANGEREQUEST. The app neither reads a foreign TSF manager through its own thread nor injects code to obtain one. IME profiles, inaccessible/elevated/remote/secure contexts and conflicting thread layouts are rejected. Treat a desktop/editor mismatch as unsupported and retain the result in this matrix. Native message delivery and focus changes have no transactional API; final identity checks plus fixed original HWND addressing limit races but cannot retract a message after delivery/timeout.
